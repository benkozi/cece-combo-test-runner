## Pre-refinement facts (2026-09-11)

Verified on `feat/run-on-rdhpc` at `fe82130`:

1. `resolve_output_roots`: under `docker` an absolute
   `--combo-output-root` must lie under `/work`; under `native`/`slurm`
   **any absolute host path is accepted** and the driver writes there.
   `--combo-clean-root` then `shutil.rmtree`s that resolved root; without
   the flag an existing root is a usage error. Nothing checks that the
   directory being removed was produced by the harness.
2. `cece.update_source` renders, for an existing clone: `git fetch
   origin`, `git checkout <ref>`, `git pull --ff-only origin <ref>`,
   `git submodule update --init --recursive`; a missing clone is
   `git clone --recurse-submodules --branch <ref>`; with the flag off an
   existing clone is used exactly as-is (no git mutation). Both paths
   then guard `extern/helm/libs`.
3. Timeouts: `harness.run_timeout_s` → `CECE_RUN_TIMEOUT_S`, a **cap**
   on the suite's per-combo `timeout_s`; the effective value bounds the
   driver. Under `slurm` it becomes the job's `--time` rounded up to
   minutes, and the harness's outer wait is `timeout_s +
   CECE_SLURM_QUEUE_WAIT_S` (default 3600 s), which is where queue time
   goes. The run config has **no knob** for the queue allowance
   (`harness.env` targets the jobs under slurm), a gap already recorded
   in the feature doc's "queue wait ceiling" note.
4. `harness.suite_config` is passed verbatim (shell-quoted) as
   `--suite-config=<selector>`; the selector is a regex fullmatched
   against suite file names, and **every match runs** as one
   multi-suite session over a flat output root — the existing harness
   behaviour, unchanged by the CLI.
5. CECE-specific wording in the new code: `src/cli/__init__.py`
   docstring ("CECE source … CECE unit tests … Slurm batch job" — also
   stale), `main.py`'s argparse description ("CECE source"), and the
   README's RDHPC paragraphs. The settings (`CECE_*`), the driver path,
   `cece.` run-config section, and `docs/ursa-runbook.md` step 3–4 are
   CECE by nature today; the CATChem spike's Phase B (`Application`
   adapter) is where they generalize.
6. Open issues: #5 (this feature), #7 benchmarking, #8 bash env/setup
   scripts, #9 CECE tests. No issue yet for suite-declared inputs or for
   Phase B.

## Responses

### 1. `harness.output_root` — "would an absolute path allow the data to be written arbitrarily?" — **answer + change**

Yes, under `native`/`slurm`: any absolute path is written to (docker
limits it to the checkout mount). That is intended — scratch layouts
differ — but the paired `--combo-clean-root` makes it a footgun: a
mistyped absolute root plus `clean_root: true` (the template default)
removes whatever is there. **Change:** the clean-root guard refuses to
remove a directory that is not a previous harness output root — one
that has no `run.yaml` at its top — with a message telling the user to
move it aside. A prior harness root is still wiped as today. Small:
one condition in `pytest_sessionstart`, one harness test (an existing
non-harness directory with `--combo-clean-root` → `UsageError`, nothing
removed), README's `--combo-clean-root` sentence. Template comment on
`output_root` states both facts (relative → under the checkout;
absolute → anywhere the runtime can write).

### 2. `data.examples` — "generalize now; download and baselines are suite-specific" — **out of scope → issue**

Agreed on the direction: an example is a suite whose inputs happen to be
downloadable by CECE's script, and inputs and baselines belong to the
suite, not to the run config. Not in this PR — it changes the suite
model, the data stage, and (with a public baseline store) the baseline
settings, and none of it is needed for the Ursa run. Issue shape:

- `SuiteConfig.inputs: list[InputFile]` (`url`, `dst` relative to the
  checkout's `data/`, optional `sha256`), with the CECE example suites
  (`ex1`…`ex7`) declaring theirs from `examples/common.py`'s mapping;
  the CLI's `data` stage stages the inputs of the **selected** suites
  (`harness.suite_config`) and `data.examples` goes away.
- Baselines: `baseline_comparisons` is already per suite; what is global
  is the store root. Fold into the same issue the standing TODO of a
  downloadable store, i.e. a per-entry `url` beside `ulid`.
- Until then `data.examples` stays, described as "CECE example ids whose
  inputs the data stage downloads".

### 3. `cece.update_source` — "does this do a git pull? recurse submodules?" — **answer + doc**

Off (default): an existing clone is used as-is, no git command touches
it. On: fetch, checkout the configured ref, fast-forward-only pull, then
`submodule update --init --recursive`; a dirty tree or diverged branch
makes git fail rather than discard anything. A fresh clone always uses
`--recurse-submodules`. **Change (doc only):** the template comment and
the `update_source` field description say exactly this, including
"recursive".

### 4. `harness.run_timeout_s` — "does this account for waiting in the queue?" — **answer + change**

No, deliberately: it caps the driver's run time (the suite's
`timeout_s`), and under slurm it is the job's `--time`. Queue time is
covered by a separate allowance, `CECE_SLURM_QUEUE_WAIT_S` (3600 s by
default), which the harness adds to its outer wait; past that it
cancels the job. The gap is that the run config cannot set it.
**Change:** `slurm.queue_wait_s` (default 3600, description says what
it is) rendered as `export CECE_SLURM_QUEUE_WAIT_S=…` in the harness
stage; the Ursa template shows it beside `qos` with the note that
`batch`-QOS waits can be hours. The state-aware wait (poll `squeue`,
unbounded while pending) stays deferred as recorded in the feature doc.

### 5. `harness.suite_config` — "can we run multiple suites?" — **answer + doc**

Yes, unchanged from the harness: the value is a regex selector, every
match runs in one session, e.g. `suite_config: 'ex[0-9]-suite.yaml'`
runs the seven example suites over one flat output root, each combo its
own Slurm job under slurm. **Change (doc only):** the template comment
says so with that example, and one stage test renders a regex selector
to confirm the quoting survives (`'--suite-config=ex[0-9]-suite.yaml'`).

### 6. `src/cli/__init__.py` — "keep it application agnostic" — **change**

Reword: "assembles a run — source checkout, driver build, input data,
the pytest session — of the application under test from one YAML run
config". Also drops the stale "CECE unit tests" and "Slurm batch job".

### 7. `src/cli/main.py` — "instead of CECE maybe target driver" — **change**

The argparse description becomes "…: target-driver source and build,
input data, the pytest session — on this node; under the slurm runtime
each driver run is a Slurm job". The `_INDEX` comment's "CECE-tests
stage" becomes "the application's own tests (issue #9)".

### 8. `README.md` prerequisites — "application agnostic please" — **change (wording) + out of scope (names)**

The RDHPC section and the touched prerequisite bullets are reworded to
"the target driver" / "the application checkout" where they describe
the mechanism. What stays CECE-specific is the vocabulary the harness
actually has today — `CECE_*` settings, `cece_standalone_driver`, the
`cece.` run-config section, `cece/cece-dev` — because there is one
application; renaming those is the CATChem spike's Phase B (the
`Application` adapter, `application:` discriminator, per-app settings).
**Out of scope → issue**: "Phase B: extract the `Application` adapter
(CECE-only, zero behaviour change)" so the README, run config, and
settings can drop the CECE prefix in one pass. A single sentence in the
README says the harness targets CECE today and names that issue.

## Issues to open (out of scope here)

### Suites declare their own inputs and baseline sources; retire "example" (response 2)

Premise (already true today): an "example" is just a configuration.
Every runnable shipped configuration has a checked-in suite — the
coverage guard `test_every_runnable_example_has_a_suite_file` fails
when a new one appears without one — and those suites run the
configurations through the full pipeline (assertions, stats, plots,
report rows). The older `--run-examples` path runs the same
configurations verbatim through CECE's entrypoint, asserts exit code
only, writes no report rows, and is unsupported under the slurm
runtime; it is redundant once a configuration is a suite.


- Add `inputs:` to the suite config: a list of `{url, dst, sha256?}`
  entries, `dst` relative to the application checkout's `data/`; unknown
  keys rejected like everything else in the suite model.
- Give the seven CECE example suites their `inputs` from the mapping in
  CECE's `examples/common.py`, so an example is just a suite with
  downloadable inputs; drop `data.examples` from the run config.
- Make the CLI's `data` stage (and `--run-examples`' download pass)
  stage the inputs of the **selected** suites only, skipping files that
  already exist with a matching checksum.
- Add a per-entry `url` beside `ulid` in `baseline_comparisons`, fetched
  into `CECE_BASELINE_ROOT_DIR` when absent, and turn
  `CECE_ENABLE_BASELINE_COMPARISONS=false` back on in CI and the Ursa
  template once the store is reachable.
- Record staged inputs and fetched baselines (path, source, checksum) in
  `run.yaml`.
- Retire the example-specific machinery: `--run-examples`,
  `src/tests/test_examples.py`, `src/examples.py`, and the
  `examples-report.md`; keep the coverage guard (renamed to
  "every shipped configuration has a suite") as the one place the word
  "example" survives, since the configurations live in CECE's
  `examples/config/`. Suite ids stay as the configuration file names
  give them (`ex3-suite.yaml`).
- Vocabulary in README, design.md, and the run config: "configuration"
  and "suite", not "example"; `data.examples` becomes the suites'
  `inputs` per the first bullet.

### Extract the `Application` adapter — spike Phase B (response 8)

- Introduce an `Application` protocol (driver path, config model,
  container image, environment prefix, output-file naming) with a
  registry holding one entry, CECE, and an `application:` discriminator
  in the suite config defaulting to it.
- Move the CECE-specific pieces behind it: `models/cece_config.py`,
  the `CECE_*` settings group, `cece_standalone_driver`, `cece/cece-dev`,
  the `cece.` run-config section — leaving enumeration, session
  machinery, stats, plots, comparison, reporting, and the runtimes
  shared.
- Zero behaviour change: every dry-run artifact byte-identical apart
  from ULIDs, the harness suite and the maccity run green, verified
  before and after.
- Rename the generic vocabulary in README, the run config, and the
  runbook to "the application" / "the target driver"; keep the CECE
  names only inside the CECE adapter and its settings.
- Leave CATChem itself to Phase C (its adapter, settings, and a
  sweep-less smoke suite).
